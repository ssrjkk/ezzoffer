## 1. Миссия и принципы

**Продукт:** автоотклики на вакансии, кабинет соискателя, Telegram-бот.

| # | Принцип | Что это значит на практике |
|---|---------|----------------------------|
| P1 | **Правда о происхождении** | Каждый факт имеет `origin`: `real`, `simulated`, `user`, `ai`. Лучше отсутствие, чем неправда. |
| P2 | **Необратимое — только с человеком** | Отклик уходит после тапа или по правилу, которое человек сам утвердил. |
| P3 | **Идемпотентность** | Любое внешнее действие безопасно повторить: второй раз эффекта нет. |
| P4 | **Минимум данных** | Секреты не в открытом виде, не в логах, не в сообщениях бота. |
| P5 | **Проверка, которая не падает, — не проверка** | Поведенческие тесты вместо сканирования исходников. Каждый тест обязан уметь упасть. |

### Ответы Фазы 0

| # | Вопрос | Ответ |
|---|--------|-------|
| 1 | Колонка происхождения в `applications`? | **Нет.** `src/lib/db.ts`, таблица `applications`: есть `status TEXT NOT NULL DEFAULT 'sent'`, колонки `origin` нет. Сценарий «статус sent» одинаков для реального и смоделированного отклика — это главный риск продукта (P1 не выполнен). |
| 2 | Где стартует планировщик, защищён ли от двойного запуска? | `src/lib/bootstrap.ts:59` — `setInterval`. От повторного вызова `register()` в том же процессе защищён флагом `schedulerStarted` (`bootstrap.ts:42-43`). **Второй инстанс и два тика внутри интервала не защищены**: `tick()` запускается на каждом тике без проверки занятости, блокировки в БД нет. |
| 3 | Как хранятся токены hh и пароль SMTP? | Токены hh — обычный `TEXT` в таблице `users`: `db.ts:45` (`hh_token`), `db.ts:47` (`hh_refresh_token`). Шифрования нет. Пароль SMTP в БД не хранится вовсе, берётся из окружения (`mail.ts:42`). Риск — токены в бэкапе файла БД. |
| 4 | Вызывается ли `seed` в продовых путях? | Демо-аккаунт из `npm run seed` в коде `src/` не создаётся — только скрипт. Но `ensureLocalSeeded()` (`vacancies/index.ts:226`) вызывается из четырёх мест (`:236`, `:260`, `:273`, `:285`) и наполняет каталог демо-вакансиями **на любом запуске**, включая прод. Это заполнение каталога, а не аккаунт, но визуально неотличимо от живых данных. |
| 5 | Что делает webhook при повторном `update_id`? | Ничего особенного: `update_id` только читается и логируется (`telegram/webhook/route.ts:39`). Таблицы отметок нет, поэтому повтор Telegram приведёт к **повторному эффекту**. Инвариант I11 не выполнен. |
| 6 | Что происходит при отклике на вакансию trudvsem? | Отправки не происходит: `canApply` есть только у hh-провайдера, `autoapply.ts:490` проверяет его и при `false` пропускает вакансию. Расхождение с картой снято: README нигде не обещает отклик по trudvsem, это ручной лид. |
| 7 | Какие роуты вне идиома? | Один: `/api/auth/me` — обработчик 1, вызовов `requireUser` 0 (`auth/me/route.ts`). Это **правильное** исключение: маршрут и должен отвечать без сессии, иначе фронт не узнает, что вышел. Остальные 36 на идиоме. |
| 8 | Как разбирается тело, что не покрыто? | Через `readJson` везде, кроме `/api/telegram/webhook` — там `req.json()` напрямую, что правильно: тело приходит от Telegram и гасить его нечем. Битое тело, мусорный идентификатор и отсутствие сессии проверяются поведенчески по всем 37 роутам (`tests/routes-malformed-body.test.ts`). |

## 5. Дорожная карта

Порядок важен: сначала правда и необратимость, потом бот, потом рост.

### Фаза 1 — Правда и безопасность

- ✅ Колонка `origin` (`real | simulated | user | ai`) в откликах; миграция
  вперёд и идемпотентная (`migrateApplicationsOrigin`: дефолт `user`,
  backfill hh→`real`). Таблица `events` создана сразу с origin-CHECK
  (писателей пока нет — появятся в Фазе 3).
- Поле `mode` у пользователя: `demo | live`. `live` — только после подключения hh и явного согласия.
- В `demo` симуляция работает и ничего наружу не уходит. В `live` симуляции нет.
- Баннер в layout кабинета в `demo`; та же пометка в боте и на воронке.
- `ensureLocalSeeded()` не должен наполнять каталог на проде без явного флага.
- Токены hh шифруются в БД, ключ из окружения.

**Готово когда:** I5, I6 покрыты тестами; в `live` нет ни одной симулированной строки.

### Фаза 2 — Необратимость

```sql
CREATE UNIQUE INDEX IF NOT EXISTS ux_applications_once
  ON applications(user_id, source, external_vacancy_id);
CREATE TABLE IF NOT EXISTS scheduler_lock (
  name TEXT PRIMARY KEY, holder TEXT NOT NULL, expires_at INTEGER NOT NULL
);
```

- Порядок: `INSERT pending` → внешний запрос → `UPDATE sent` или `failed`.
- Сверка зависших `pending` со списком откликов на стороне hh; слепых повторов нет.
- Блокировка планировщика в БД плюс защита от наложения тиков внутри интервала.
- Рубильники: `AUTOAPPLY_ENABLED`, `AUTOAPPLY_DRY_RUN`, пауза пользователя.
- Дневной лимит считается запросом к БД, а не счётчиком в памяти.
- Журнал `apply_events` только для добавления.

**Готово когда:** I4, I8 покрыты; тест «`fetch` успешен, следующий `UPDATE` упал» не даёт второго отклика.

### Фаза 3 — Фундамент бота

```sql
CREATE TABLE events (id INTEGER PRIMARY KEY, user_id INTEGER NOT NULL,
  kind TEXT NOT NULL, origin TEXT NOT NULL CHECK (origin IN ('real','simulated','user')),
  entity_type TEXT, entity_id INTEGER, payload TEXT NOT NULL,
  dedupe_key TEXT UNIQUE, created_at INTEGER NOT NULL);
CREATE TABLE outbox (id INTEGER PRIMARY KEY, chat_id INTEGER NOT NULL,
  event_id INTEGER REFERENCES events(id), priority INTEGER NOT NULL,
  body TEXT NOT NULL, markup TEXT,
  state TEXT NOT NULL DEFAULT 'pending', attempts INTEGER NOT NULL DEFAULT 0,
  next_try_at INTEGER NOT NULL, tg_message_id INTEGER);
CREATE TABLE tg_updates (update_id INTEGER PRIMARY KEY, seen_at INTEGER NOT NULL);
```

- Webhook: секрет за постоянное время → запись `update_id` (конфликт = повтор) → 200 сразу → воркер.
- Воркер outbox: приоритеты, токен-бакет, 429 (`retry_after`) и 403 (чат гасится).
- Команды латиницей через `setMyCommands`; русские слова как запасной вариант.
- Данные кнопки: `v1|act|entity_id|card_ver`; сервер проверяет владельца и версию.
- Привязка аккаунта: только личный чат, ограничение попыток, уведомление в кабинете.

**Готово когда:** I11 покрыт; фейковый `api.telegram.org` подтверждает дубль апдейта, чужую кнопку, устаревшую карточку, 403 и 429.

### Фаза 4 — Живой поток

- События только `origin = 'real'`, дедупликация по `dedupe_key`.
- P0 приглашение (сразу, с кнопками, пробивает тихие часы); P1 смена этапа; P2 «просмотрено» в дайджест; отказы пачкой раз в день.
- Тихие часы по IANA-поясу. Утренний дайджест опционально.

**Готово когда:** p95 «событие → сообщение» меньше минуты на фейковом API; P0 переживает падение воркера.

### Фаза 5 — Триаж и доверие

- Карточка вакансии: объяснение совпадения, кнопки «Откликнуться / Пропустить / Скрыть компанию».
- Причины пропуска превращаются в явные правила фильтров; правило видно и удаляется.
- Отправка с отменой: очередь 5–10 минут, «Отменить» и «Править письмо».
- **Проверка утверждений:** навыки, годы, компании и цифры из письма сверяются с резюме; неподтверждённое блокирует отправку.
- Модель предлагает черновик, но не вызывает «отправить» (I7).

**Готово когда:** I7 покрыт; письмо с непроверенным фактом не доходит до очереди.

### Фаза 6 — Интервью

- Сущность `interview`, дата разбирается из текста и подтверждается кнопками.
- `.ics`, напоминания за сутки, час и 15 минут (UTC библиотекой, знающей DST).
- Сводка накануне, разбор после встречи, follow-up через 5 дней тишины.
- Черновики ответов рекрутёру; отправка только по тапу.

### Фаза 7 — Рост

- Пересылка ссылки или текста вакансии → разбор по схеме → подтверждение → учёт.
- Inline-режим. Mini App с валидацией `initData` по HMAC и свежести `auth_date`.
- Недельный разбор только по `origin = 'real'`.

### Трек H — Гигиена

- **Dependabot:** `better-sqlite3` 12→13 исключить (нужен C++-тулчейн); `@types/node` держать на мажоре минимально поддерживаемого Node; TypeScript 5.9→7 только после проверки typescript-eslint и Next.
- **README:** опечатки, дубль Installation/Usage, пустой бейдж TypeScript.
- **Эксплуатация:** бэкап `data/` с проверкой восстановления, WAL, эндпоинт здоровья, сбор ошибок.
- **Персональные данные:** политика обработки, согласие, удаление данных из кабинета и бота.

## 6. Протокол работы агента

1. **Читай перед правкой:** сам файл, его тест и места вызова.
2. **План из 3–5 строк**, потом правки. Одна задача — один коммит.
3. **Для инварианта сначала тест.** Убедись, что он краснеет на сломанном коде, потом чини.
4. **Не расширяй задачу.** Найденное сбоку — в «Находки», молча не чини.
5. **Миграции БД:** только вперёд, идемпотентные, проверенные на пустой и на заполненной базе.
6. **Ворота перед «готово»:** `tsc`, lint, все тесты, `git status` чист.
7. **Нельзя без явного разрешения:** `git push`, удаление данных или файлов вне задачи, мажорные обновления зависимостей, внешние сетевые вызовы, включение реальных отправок.
8. **Не уверен — остановись и задай один вопрос.**

## 7. Стратегия тестов

- unit домена (скоринг, парсеры, лимиты);
- **поведенческие тесты роутов** по всем 37: нет сессии, чужой id, битый id, битое тело;
- фейковые внешние API (hh, Telegram, SMTP) на подмене `fetch` со счётчиком вызовов;
- Chromium для UI и баннеров;
- инварианты живого каталога.

**Уроки прошлых прогонов:**
1. Считать код, а не регулярки: страница не «невыщитана», если в ней `parseParamId`, проверка владения и `sanitizeExternalUrl`.
2. Не искать вызов «где угодно», включая строку импорта.
3. Считать обработчики против вызовов, а не «хотя бы один в файле».
4. Утверждение, которое нельзя сломать, удалять, а не оставлять.
5. Непокрытое записывать прямо в файле теста.
6. Поведенческий тест бьёт по **работающей сборке**: правка исходников его не роняет, пока сервер не пересобран.
